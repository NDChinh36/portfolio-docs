## Kết quả dự án

- Calculator designed to serve three trader groups: new traders (liquidation price), regular traders (PnL and ROE) and advanced traders (full parameter set)

---

## Bối cảnh nghiệp vụ

Users needed a calculation tool to estimate trading outcomes before placing orders. Many users — especially new traders — were leaving the platform to use external tools to calculate PnL or liquidation price, then returning to trade.

This was the first feature I owned as a BA at Nami Innovation, immediately after transitioning from a marketing role.

---

## Vai trò của tôi trong dự án

- Collected user feedback through CS team interviews
- Analyzed competitor calculator tools (Binance, OKX, Bybit)
- Defined feature scope and formula requirements
- Wrote PRD and supported functional specification
- Aligned UI/UX flow with Design and formula logic with Development
- Supported QA testing for formula accuracy

---

## Bài toán BA cần giải quyết

- **User need validation** — Before defining scope, I needed to confirm what calculation problems users actually had, not what Product assumed.
- **Formula specification** — PnL, liquidation price and required margin formulas needed to be defined precisely enough for Dev to implement correctly and QA to verify.
- **Scope prioritization** — Multiple trader groups had different needs. Scope had to be prioritized to avoid building too much for MVP.
- **Formula accuracy** — Calculator outputs must match trading product rules. Wrong formulas would undermine user trust in the platform.

---

## Cách tiếp cận của BA

### Bắt đầu từ CS team

Instead of starting from assumptions, I interviewed the CS team to identify the most common user calculation questions. This revealed three distinct trader groups with different needs — driving the scope and tab-based layout.

### Nghiên cứu competitor trước khi define scope

I analyzed calculators on Binance, OKX and Bybit to benchmark features, identify UX patterns and understand what Nami needed to include or could simplify.

### Formula definition là deliverable của BA

I documented each formula explicitly as a BA deliverable — not just as implementation notes. This gave Dev a clear reference and gave QA expected values to validate against.

---

## Business Rules cốt lõi

| Rule | Behavior |
| --- | --- |
| **Required fields** | All required inputs must be completed before calculation runs |
| **Input validation** | Invalid numeric inputs are blocked; appropriate error message shown |
| **Real-time calculation** | Results update automatically when any input changes — no submit button needed |
| **Formula alignment** | Calculator formulas must match the trading product's underlying calculation logic |
| **Result labeling** | Results are clearly labeled as estimates, not guaranteed outcomes |
| **Edge case: leverage = 1** | No liquidation price displayed at 1x leverage (no liquidation risk) |

---

## Luồng nghiệp vụ chính

1. User selects calculator type (PnL / Liquidation Price / Required Margin)
2. User enters trading parameters (entry price, exit price, quantity, leverage, margin mode)
3. System validates inputs
4. System calculates and displays estimated result in real-time
5. User adjusts parameters as needed
6. User uses result as reference before placing an order

- **QA Formula Checklist** — expected outputs for key input combinations

## Phối hợp với các team

### Clarify formula với Dev

I walked Dev through each formula in a dedicated session — including edge cases like Cross Margin liquidation (which depends on full account equity, not just position margin) and the difference between ROE and PnL percentage. This prevented misunderstanding during implementation.

### Hỗ trợ QA kiểm tra formula

I prepared a formula checklist with specific numeric examples — input values and expected outputs — so QA could verify formula accuracy without deriving the expected results themselves.

### Quyết định UX với Design

I worked with Design on two key UX decisions: real-time calculation (no submit button needed) and the "Fill from position" button (lets users pull parameters from an open order directly into the calculator). Both came from competitor analysis and CS feedback.

## Kiểm tra trước release

- Reviewed formula outputs against expected values from the formula spec
- Confirmed edge case behavior (leverage = 1, Cross mode disclaimer)
- Validated real-time calculation trigger behavior across input types
- Supported QA sign-off

---

## Bài học rút ra

- **CS team is the fastest path to user insight** — for a utility tool like a calculator, CS feedback was more accurate and faster than user surveys or assumptions.
- **Formula specification is a core BA deliverable** — even for a "simple" calculation feature, formula definitions need to be explicit, testable and owned by BA from the start.
- **Domain knowledge before spec writing** — transitioning from marketing, I had to quickly learn futures calculation concepts before I could write correct requirements. Time spent on domain research first paid off in spec quality.
