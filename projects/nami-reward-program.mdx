# Reward Program Feature

> **Real Project — Nami Innovation** This case is based on my real work as a Business Analyst. Sensitive information has been generalized or anonymized.

## Project Overview

- **Role:** Business Analyst
- **Company:** Nami Innovation
- **Timeline:** 1/2025 – 6/2025
- **Platform:** Web / Mobile
- **Domain:** Growth / Reward System
- **Team:** Product, Growth, Content, CS, BI, Dev, QA, UI/UX

## Outcome

- 20K\+ user engagement
- 60%\+ volume increase

This outcome was a team result. My BA contribution focused on requirement clarification, reward logic, campaign rules, tracking and delivery support.

## Business Context

Nami needed a reward system to support user engagement campaigns based on in-app actions.

The challenge was not only giving rewards, but defining clear conditions, limits, eligibility, anti-abuse rules and tracking metrics so that Product, Growth, Engineering, QA, CS and BI could work from the same understanding.

## My Role as BA

- Worked with PO and Growth/MKT to clarify campaign goals.
- Defined reward conditions, limits and automation rules.
- Wrote PRD and supported functional specification.
- Coordinated with Design, Dev, QA, Content, CS and BI.
- Tracked campaign data and refined logic based on performance.

## BA Problems to Solve

- Campaign requirements changed depending on business goals.
- Reward conditions needed to be clear enough for Dev and QA.
- Abuse scenarios needed to be considered before launch.
- Growth needed tracking metrics to evaluate campaign performance.
- CS needed clear rules to explain reward behavior to users.

## Core Business Rules

- User must complete eligible in-app action before reward distribution.
- Reward amount depends on campaign configuration.
- Each campaign has a total budget cap.
- Each user has a per-user reward cap.
- Duplicate or suspicious actions should be excluded.
- Campaign performance must be tracked after launch.
- Reward status must be visible enough for CS and operation follow-up.

## Key BA Decisions

### Decision 1 — Configurable Campaign Logic

**Context:** Each campaign had different target actions and reward conditions.

**Problem / Risk:** Hardcoding each campaign would slow down future launches and increase rework.

**BA Recommendation:** Define campaign logic as configurable rules.

**Trade-off:** Initial setup becomes more structured and requires clearer input from Growth.

**Expected Impact:** Faster campaign rollout and easier maintenance.

### Decision 2 — Budget Cap and Per-user Cap

**Context:** Reward campaigns can create financial exposure if not controlled.

**Problem / Risk:** Without caps, reward distribution could exceed campaign budget.

**BA Recommendation:** Define both campaign-level budget cap and user-level cap.

**Trade-off:** Some users may stop receiving rewards after reaching the cap.

**Expected Impact:** Better cost control and lower abuse risk.

### Decision 3 — Anti-abuse Rules from PRD Stage

**Context:** Reward features can attract unintended user behavior.

**Problem / Risk:** If anti-abuse rules are added too late, Dev and QA may need rework.

**BA Recommendation:** Include anti-abuse rules from the first PRD version.

**Trade-off:** PRD takes more time upfront.

**Expected Impact:** Fewer loopholes and clearer QA scenarios.

## Main Flow

1. Growth team defines campaign goal.
2. BA clarifies eligible user actions and reward conditions.
3. User completes an eligible in-app action.
4. System checks eligibility and anti-abuse rules.
5. System calculates reward amount.
6. Reward is distributed, rejected or marked pending.
7. BI/Growth tracks campaign performance.
8. Campaign logic is refined if needed.

## Important Edge Cases

- User completes action after campaign ends.
- User reaches per-user reward cap.
- Campaign reaches total budget cap.
- Duplicate action is detected.
- Suspicious behavior is detected.
- Reward distribution fails.
- CS needs to verify reward status for a user.

I translated campaign logic into clear rules, edge cases and expected behavior so Dev and QA could implement and validate consistently.

### CS and BI

I supported CS with rule explanations and aligned tracking needs with BI to monitor campaign performance after launch.

## Validation Before Release

- Reviewed campaign setup and reward conditions.
- Checked eligibility and cap logic with QA.
- Validated important edge cases.
- Supported CS guide and release communication.
- Reviewed campaign tracking metrics after launch.

## Lessons Learned

- Growth features still need clear business rules and edge case handling.
- Reward logic should be configurable when campaign requirements change frequently.
- Anti-abuse scenarios should be defined before implementation.
- Metrics should be agreed early so post-launch performance can be evaluated.
