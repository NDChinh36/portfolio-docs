## Business Context

Nami Innovation needed an **internal transfer feature** to allow users to move assets between accounts within the Nami ecosystem — without withdrawing to an external platform.

The feature involved multiple account types (Spot, Futures), validation rules, balance locking logic and clear user flows despite complex backend behavior.

**Why this required careful BA work:** A wrong validation rule in a financial transfer feature can allow invalid transfers or block legitimate ones. Rules needed to be precise, agreed upon and fully tested before launch.

## BA Problems to Solve

- **Transfer path rules** — Not all account-to-account combinations were supported. Clear rules were needed to define what was allowed and what was blocked.
- **Available vs. total balance** — Users with open Futures positions have locked margin. Using total balance for validation would allow invalid transfers that could trigger unexpected position liquidation.
- **Receiver validation** — Invalid or inactive receiver accounts needed to be detected before confirmation, not after submission.
- **Edge case coverage** — Financial transactions have many failure scenarios. Dev and QA needed a complete edge case spec to ensure full coverage.

---

## Core Business Rules

| Rule | Behavior |
| --- | --- |
| **Eligible transfer paths** | Spot → Spot (same user), Spot → Spot (other user P2P), Spot ↔ Futures (same user) |
| **Blocked paths** | Futures → Futures cross-user is blocked to reduce risk control complexity |
| **Balance validation** | Transfer amount is validated against available balance, not total balance |
| **Minimum amount** | Each asset has a configured minimum transfer amount |
| **Receiver validation** | Receiver account must be active; validated before confirmation screen |
| **Threshold verification** | P2P transfers above a configured threshold require additional verification |
| **Duplicate prevention** | Duplicate submissions are rejected |

## Key BA Decisions

### Decision 1 — Block Futures-to-Futures Cross-user Transfer

**Context:** The team discussed whether Futures accounts should support P2P transfers, similar to Spot accounts.

**Problem / Risk:** Futures margin is partially locked when positions are open. Cross-user Futures transfer creates risk control complexity and potential for margin manipulation. Engineering raised concerns about race conditions in margin validation.

**BA Recommendation:** Block Futures-to-Futures cross-user transfers entirely. Supported paths: Spot ↔ Spot cross-user P2P, Futures ↔ Spot same-user rebalance only.

**Trade-off:** Removes an edge use case for traders wanting to move margin directly between different accounts. Trade-off accepted — the use case is rare.

**Expected Impact:** Simpler validation rules, alignment with Futures risk model, removes a class of potential bugs.

---

### Decision 2 — Validate Against Available Balance, Not Total Balance

**Context:** An early Dev draft validated transfers against total balance.

**Problem / Risk:** Users with open Futures positions have locked margin included in their total balance. Validating against total balance would allow a transfer that leaves insufficient margin to maintain open positions — potentially triggering unexpected liquidation.

**BA Recommendation:** Validate against available balance, calculated as total balance minus locked margin. Requires a call to the Futures engine before the validation step.

**Trade-off:** Adds one API call to the validation flow, slightly increasing latency.

**Expected Impact:** Prevents users from accidentally liquidating Futures positions when transferring funds.

---

### Decision 3 — Threshold-based Verification for P2P Transfers

**Context:** Security team wanted OTP for all P2P transfers. UX team wanted minimal friction.

**Problem / Risk:** Requiring OTP for all P2P transfers adds unnecessary friction for small amounts. Removing OTP entirely creates security risk for large transfers if an account is compromised.

**BA Recommendation:** Apply verification only when transfer amount exceeds a configured threshold. Internal same-user transfers (Spot ↔ Futures rebalance) do not require verification.

**Trade-off:** Threshold value needs to be defined and maintained over time.

**Expected Impact:** Balances security with UX — low friction for small transfers, stronger verification for large ones.

## Main Flow

1. User selects transfer type (internal same-user or P2P to another user)
2. User selects source account and asset
3. For P2P: user enters receiver UID or email; system validates receiver
4. User enters transfer amount
5. System validates available balance and transfer rules
6. Preview screen shows: from, to, asset, amount and fee if applicable
7. For amounts above threshold: verification step is required
8. User confirms transfer
9. System processes transaction
10. Result screen shows Success or Failure with reason

---

## Important Edge Cases

- Invalid or inactive receiver → error shown before confirmation; transfer blocked
- Insufficient available balance → Submit disabled; clear message displayed
- Blocked transfer path → option hidden or disabled; no confusing error message
- User has open Futures position → available balance reduced by locked margin amount
- Transfer amount equal to full available balance → allowed
- Duplicate submission → second request rejected
- Debit succeeds but credit fails → rollback triggered; incident logged; user notified
- User exits app before result screen → transfer status retrievable on return

## Collaboration with Dev / QA / UIUX

### Align with Engineering

I clarified the available balance calculation requirement early — specifically that validation must call the Futures engine to retrieve locked margin before the validation step. Catching this before development started prevented a late-stage change that would have required significant rework.

### QA Support

I provided QA with a complete edge case matrix including specific test scenarios — for example, the exact behavior when a user has a locked Futures position and transfers the maximum available amount. QA used this to build test cases without deriving the logic independently.

### Growth and Brand alignment

This project included a launch communication review with Brand and a metric definition session with Growth to determine how transfer adoption would be measured after release.

## Lessons Learned

- **Invest in user flow before PRD** — having a clear flow before writing the full PRD reduced revision cycles and saved communication overhead across the team.
- **Available vs. total balance must be explicit** — this distinction is easy to miss in early drafts but critical in fintech. It should be an early clarification question in any transfer spec.
- **End-to-end ownership requires follow-through** — ownership means staying involved through QA, UAT and release, not just completing the PRD.
